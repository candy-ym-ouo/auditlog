## 1. 项目概述与设计目标

### 1.1 背景

在业务系统中，"谁、在什么时间、对什么对象、做了什么操作"是关键审计信息。普通数据库日志存在两个信任缺陷：

1. **可静默篡改**：拥有数据库写权限的人（或入侵者）可以直接 UPDATE/DELETE 历史日志，事后无从察觉；
2. **不可追溯**：日志之间彼此孤立，缺少"上下文链"，无法还原一次操作在时间线上的前后关联。

### 1.2 设计目标

| 编号 | 目标 | 度量方式 |
| --- | --- | --- |
| G1 | 每条关键操作以密码学哈希链方式落库，篡改可检测 | 任意篡改后，全链验证必须报告失败 |
| G2 | 提供完整验证能力：全链 / 区间 / 链头 / 抽样 | 验证接口返回结构化报告 |
| G3 | 支持归档：旧记录定期离链归档，且不破坏哈希链 | 归档后全链验证仍通过 |
| G4 | 支持追溯：多维度查询与单条上下文回溯 | 查询接口 + 上下文接口 |
| G5 | 持久化记录并管理迁移：启动自动迁移到最新 schema | schema_migrations 版本表 |
| G6 | 提供 REST API 与简单前端界面 | 前端六大面板可完成写入/查询/验证/归档 |
| G7 | 提供测试与一键完整验证 | 单元 + 集成 + 端到端验证脚本 |

### 1.3 术语表

| 术语 | 含义 |
| --- | --- |
| 审计条目（Entry） | 一条不可变的关键操作记录，是哈希链的基本单元 |
| 哈希链（Hash Chain） | 条目之间通过 `prev_hash → hash` 串行引用的链表结构 |
| 创世条目（Genesis） | 链上第一条记录，其 `prev_hash` 为全零哈希 |
| 链头（Head） | 最近一次写入的条目，链的末端 |
| 验证报告（Report） | 验证过程的完整结果，含状态、断点、耗时、条目计数 |
| 归档批次（Batch） | 一次归档操作产生的一组条目及其清单（manifest） |
| 完整验证（Full Verify） | 对主库与全部归档批次做一次端到端链完整性验证 |

## 3. 核心业务逻辑：哈希链

### 3.1 链的结构

审计条目在逻辑上构成一条单向链表。每条条目除业务字段外，还携带两个密码学字段：

```
┌────────────┐      ┌────────────┐      ┌────────────┐
│  Genesis   │ ───► │  Entry#2   │ ───► │  Entry#3   │ ───► …
│ prev=0…0   │      │ prev=h1    │      │ prev=h2    │
│ hash=h1    │      │ hash=h2    │      │ hash=h3    │
└────────────┘      └────────────┘      └────────────┘
```

- `prev_hash`：链上前一条条目的 `hash`，创世条目的 `prev_hash` 为 64 个 `0`；
- `hash`：本条目的内容摘要（见 3.2）。

### 3.2 哈希计算规则

采用 SHA-256，对条目内容做**规范化序列化**后计算。设计上必须保证"相同内容 → 相同哈希"，因此序列化时对字段顺序、JSON 格式做固定约束：

```
hash = SHA256(
    seq            (int64, 10 进制文本)
  + "|" + prev_hash
  + "|" + event_time  (RFC3339Nano, UTC)
  + "|" + actor
  + "|" + action
  + "|" + target
  + "|" + detail     (规范化 JSON：键按字典序、无多余空白)
)
```

> 字段 `id`（数据库主键）**不参与**哈希计算，因为数据库内部 ID 可能因归档/迁移而变化；`seq`（链序号）参与计算，作为链位置的锚点。
> 采用 `|` 分隔并要求字段内禁止出现 `|`（写入时校验并拒绝），避免歧义拼接攻击。

### 3.3 篡改检测原理

设链为 `E1 → E2 → … → En`，`hash(Ei)` 覆盖了 `Ei` 的全部业务字段与 `prev_hash`。若攻击者修改了 `Ek` 的任意业务字段：

1. `hash(Ek)` 失配（重算值与存储值不同）→ 定位到 `Ek`；
2. 即使攻击者重算并改写 `Ek.hash`，由于 `Ek+1.prev_hash` 仍指向旧值 → `Ek+1` 失配；
3. 攻击者必须从 `Ek` 起**重算整条后缀链**才能伪装成功。因此，只要链头哈希被可信方（如外部锚定、或定期记录在验证报告中）固定，篡改就无法隐藏。

### 3.4 追加写入流程（单条）

```
客户端 ──► 校验请求（actor/action/target 非空、detail 为合法 JSON、无 '|'）
        ──► 读取当前链头（head_seq, head_hash）          [事务内]
        ──► 组装条目：seq = head_seq + 1, prev_hash = head_hash
        ──► 计算 hash（3.2 规则）
        ──► 写入 audit_entries（INSERT）                 [同一事务]
        ──► 更新链头游标（meta 表）
        ──► COMMIT ──► 返回条目（含 hash 与 seq）
```

**并发控制**：哈希链要求严格的全局顺序。服务内置"单写者"语义：
- 所有写入经一个串行化入口（进程内 `sync.Mutex` + SQLite 事务）；
- 写事务使用 `BEGIN IMMEDIATE`，防止读写锁升级死锁；
- 归档、验证等读操作不阻塞写入（WAL 模式读写并发）。

**失败语义**：任一环节失败则整体回滚，链上不产生空洞；客户端可安全重试。

### 3.5 链头游标

链头（当前 seq 与 hash）保存在 `meta` 表（key-value）。它是验证与追加的公共锚点，读取链头与追加写入必须在同一写事务内完成，保证"读到的链头一定是最新的"。

## 4. 关键操作记录业务逻辑

### 4.1 操作分类（action 枚举，开放扩展）

| action | 语义 | 典型 target |
| --- | --- | --- |
| `login` / `logout` | 登录/登出 | 用户 ID |
| `perm_change` | 权限变更 | 角色/用户 |
| `data_modify` | 数据修改（增删改） | 业务表/记录 ID |
| `config_change` | 系统配置变更 | 配置键 |
| `export` | 数据导出 | 导出范围 |
| `archive` | 审计归档动作本身也入链 | 批次号 |

> 归档动作自身也要写入审计链（审计的审计），保证归档操作本身可被追溯。

### 4.2 写入前置校验

服务端对每个写入请求执行以下校验，任一不通过返回 `400`：

1. `actor`、`action`、`target` 非空且长度 ≤ 256；
2. `event_time` 缺省取服务端当前 UTC 时间；若携带，必须为合法 RFC3339 且不超前服务端时间 5 分钟（防时钟伪造）；
3. `detail` 必须是合法 JSON 对象（可为空对象），序列化后参与哈希；
4. 所有字段不得包含分隔符 `|`；
5. 可选的静态令牌认证（见 10.1）。

### 4.3 不可变性约定

- 审计条目**不允许 UPDATE / DELETE**：数据层接口不暴露修改/删除方法，DDL 不建相关触发器；
- 服务重启不丢数据：写入为同步落盘（WAL `synchronous=NORMAL` + 事务提交）；
- 链头只前进不后退：`seq` 单调递增，禁止回写。

### 4.4 统计口径

`audit_entries` 提供 `COUNT`、按 `action` 分组计数、当日写入数等统计，供前端总览面板使用。

## 5. 完整性验证业务逻辑

### 5.1 验证模式

| 模式 | 范围 | 复杂度 | 用途 |
| --- | --- | --- | --- |
| `full` | 全链（主库 + 归档） | O(n) | 一键完整验证、合规审计 |
| `range` | 指定 `[start_seq, end_seq]` 区间 | O(k) | 定点排查 |
| `head` | 仅校验最后 N 条 + 链头引用 | O(1)~O(N) | 快速体检 |
| `spot` | 按步长抽样（如每 100 条验 1 条） | O(n/step) | 大数据量快速验证 |

### 5.2 全链验证算法

```
prev_hash = 全零
for each entry in 按 seq 升序:
    recomputed = hash(entry 字段 + prev_hash)
    if recomputed != entry.hash          → 状态 = HASH_MISMATCH, 断点 = entry.seq
    if entry.prev_hash != prev_hash      → 状态 = LINK_BROKEN,  断点 = entry.seq
    prev_hash = entry.hash
链尾：若最后一条 hash != 记录的链头 hash → 状态 = HEAD_MISMATCH
全部通过                                          → 状态 = OK
```

### 5.3 验证结果模型

```json
{
  "status": "ok | hash_mismatch | link_broken | head_mismatch",
  "checked_entries": 1200,
  "start_seq": 1,
  "end_seq": 1200,
  "break_seq": 0,
  "break_reason": "",
  "head_hash": "9f86…",
  "archives_checked": 2,
  "duration_ms": 86,
  "verified_at": "2025-01-01T00:00:00Z"
}
```

- `status=ok`：链完整；
- `hash_mismatch`：某条目内容被改（哈希失配），`break_seq` 指向该条目；
- `link_broken`：某条目引用的 `prev_hash` 与链上前一条不符（链被插入/删除）；
- `head_mismatch`：链尾哈希与链头游标不符（链被截断/追加异常）。

### 5.4 验证与归档的联动

归档条目被搬入归档批次后，仍保留 `prev_hash`/`hash` 字段。验证器按 `seq` 全局排序读取（主库 + 归档批次合并视图），因此**归档不影响全链验证的正确性**。

## 6. 归档业务逻辑

### 6.1 归档策略

| 策略 | 配置项 | 默认 |
| --- | --- | --- |
| 按条数 | `archive.threshold`：主库条目数超过阈值即触发 | 10000 |
| 按时间 | `archive.max_age_days`：超过 N 天的条目可归档 | 90 天 |
| 手动 | API `POST /api/v1/archive` / 前端按钮 | — |
| 保留下限 | `archive.keep_min`：主库至少保留最近 N 条，防止频繁归档 | 1000 |

> 触发条件取交集：条数超阈值 **且** 存在超过保留下限的旧条目，才执行一次归档。

### 6.2 归档流程

```
1. 选取待归档条目：seq ≤ (max_seq - keep_min) 且 event_time < now - max_age_days
   （无时间条件时按条数：seq ≤ max_seq - keep_min）
2. 若待归档数 < batch_min（默认 100）→ 本次跳过（避免碎批次）
3. 事务内：
   a. 读取待归档条目（按 seq 升序）
   b. 计算批次头部：start_seq, end_seq, prev_hash(start), head_hash(end)
   c. 计算载荷哈希 payload_hash = SHA256(全部条目规范化 JSON 拼接)
   d. INSERT archive_batches（批次清单）
   e. 条目从 audit_entries 搬入 archive_entries（保留原 seq/hash/prev_hash）
   f. 删除 audit_entries 中已搬移记录
   g. COMMIT（整个批次原子完成）
4. 写入一条 action="archive" 的审计条目（归档动作入链）
5. 更新运行统计（最近归档时间、累计批次）
```

> **原子性**：批次的"搬出 + 清单落库"在同一事务内完成；任一步失败整体回滚，主库保持原状，不存在"搬了一半"的中间态。

### 6.3 批次清单（manifest）

每个批次记录：

| 字段 | 说明 |
| --- | --- |
| `batch_no` | 批次号，自增 |
| `start_seq` / `end_seq` | 覆盖的链区间 |
| `prev_hash` | 区间前一条的哈希（衔接上一段） |
| `head_hash` | 区间最后一条的哈希（衔接下一段） |
| `item_count` | 条目数 |
| `payload_hash` | 批次载荷摘要，防清单与数据不一致 |
| `archived_at` | 归档时间 |

### 6.4 归档后的能力

- **验证**：全链验证自动合并归档批次（见 5.4）；
- **导出/恢复**：提供 `GET /api/v1/archive/batches/:no` 导出批次 JSON（含清单与条目），可离线重放；
- **追溯**：归档条目仍可通过追溯接口查询（查询层合并主库与归档）。

## 7. 追溯业务逻辑

### 7.1 查询维度与过滤

`GET /api/v1/entries` 支持组合过滤：

| 参数 | 语义 |
| --- | --- |
| `actor` | 操作人精确匹配 |
| `action` | 动作精确匹配 |
| `target` | 目标模糊匹配（LIKE） |
| `from` / `to` | event_time 区间（RFC3339） |
| `seq_from` / `seq_to` | 链序号区间 |
| `page` / `page_size` | 分页（默认 1/20，上限 200） |
| `include_archived` | 是否合并归档条目（默认 true） |

### 7.2 上下文回溯

`GET /api/v1/entries/:id/context?radius=N`：返回以该条目为中心的**前后各 N 条**（含该条目本身），并附带：

- 该条目的 `prev_hash` 与 `hash`；
- 该条目与其前后条目的哈希衔接是否成立（快速上下文校验）；
- 链位置（seq）。

用途：还原一次关键操作（如权限变更）在时间线上的前后动作，支撑取证。

### 7.3 审计报告导出

`GET /api/v1/trace/report?…`：将追溯查询结果包装为审计报告 JSON：

```json
{
  "report_id": "…",
  "generated_at": "…",
  "query": { "actor": "alice", "from": "…" },
  "total": 42,
  "chain": { "first_seq": 5, "last_seq": 900 },
  "verification": { "status": "ok", "checked": 42 },
  "entries": [ … ]
}
```

报告同时附上对导出条目的**区间验证结果**，让追溯结论自带可信度。

## 8. 持久化与迁移业务逻辑

### 8.1 存储选型

- **SQLite（`modernc.org/sqlite` 纯 Go 驱动）**：单文件、零运维、事务完备，契合审计日志"追加为主、归档出库"的负载；
- WAL 模式：读写并发不互斥，验证（读）期间写入（写）不被阻塞；
- `synchronous=NORMAL`：兼顾性能与崩溃安全（WAL 下可保证提交不丢失）。

### 8.2 Schema 版本管理

- 版本表 `schema_migrations(version INTEGER PRIMARY KEY, applied_at TEXT)`；
- 每个迁移一个版本号（从 1 递增），迁移以**幂等 DDL** 编写（`IF NOT EXISTS` 等）；
- 迁移在服务启动时、任何读写之前执行（见 8.3）。

### 8.3 迁移执行流程

```
1. 打开数据库，`PRAGMA journal_mode=WAL`
2. 读取 schema_migrations 最大版本 v_current（无表则视为 0 并先建表）
3. 取已注册迁移列表（版本升序）
4. 对每个 version > v_current 的迁移：
   a. BEGIN 事务
   b. 执行该迁移的全部 DDL/DML
   c. INSERT schema_migrations(version)
   d. COMMIT
5. 任一步失败 → 回滚该版本 → 启动中止并输出错误（拒绝带半迁移状态运行）
```

### 8.4 迁移清单（规划）

| 版本 | 内容 |
| --- | --- |
| v1 | 建 `schema_migrations`、`meta`、`audit_entries` |
| v2 | 建 `archive_batches`、`archive_entries`，补充索引 |
| v3 | `audit_entries` 增加 `target` 索引（追溯查询加速） |

> 迁移可向后追加新版本，禁止修改已发布版本（保证可重复部署）。

## 9. 后台归档任务业务逻辑

### 9.1 调度器

- 独立 goroutine，按 `worker.archive_interval`（默认 60s）周期触发；
- 同时监听手动触发信号（`POST /api/v1/archive`）与停止信号（优雅停机）；
- 使用 `select` 多路复用：定时器 / 手动触发 / 上下文取消。

### 9.2 任务状态机

```
idle ──(满足策略)──► running ──(成功)──► idle
                      │  └──(失败)──► idle（记录错误、保留上次错误信息）
                      └──(取消/停机)──► stopped
```

- 防重入：`running` 期间忽略新的触发信号（用 `sync/atomic` 标志位）；
- 状态可查询：`GET /api/v1/archive/status` 返回 `{last_run_at, last_batch_no, running, last_error}`。

### 9.3 优雅停机

- 服务收到 `SIGINT/SIGTERM` 后：停止接收新写入 → 通知调度器停止 → 等待当前归档批次完成（带超时，默认 30s）→ 关闭数据库 → 退出；
- 归档批次本身是事务性的，停机中断也不会产生半批次。

## 11. 完整验证业务逻辑

### 11.1 一键完整验证

`POST /api/v1/verify {"mode":"full"}`（或命令行 `./auditlog verify`）：

1. 锁定写入（验证期间拒绝新条目，或采用"快照式"验证：先记录当前链头，仅验证到该链头为止）——设计采用**链头快照**方式，不阻塞写入；
2. 读取主库全部条目 + 全部归档批次条目，按 `seq` 全局排序合并；
3. 执行 5.2 全链验证算法（含批次衔接检查：上一批次 `head_hash` 必须等于下一段首条的 `prev_hash`）；
4. 汇总结果，写入一条 `action="verify"` 的审计条目（验证动作入链，形成验证轨迹）；
5. 返回验证报告（5.3 模型），前端展示。

### 11.2 报告内容

报告除 5.3 字段外，附加：

- 批次衔接明细（每个归档批次的 `start_seq/end_seq/head_hash` 是否衔接成功）；
- 验证范围说明（主库条目数、归档条目数、总检查数）；
- 验证动作自身的入链 seq（供复核）。

### 11.3 与测试的关系

"完整验证"既是运行时能力，也是测试脚本的**最终断言**（见 docs/05 端到端演练）：篡改演练后必须能通过完整验证发现异常。

## 12. 业务场景示例

### 场景 A：管理员操作审计（日常）

1. 管理员 Alice 登录系统 → 服务自动写入 `{actor:"alice", action:"login"}`；
2. Alice 修改了角色权限 → 写入 `{actor:"alice", action:"perm_change", target:"role:ops"}`；
3. 审计员在**前端验证面板**点击"完整验证" → 报告 `status=ok`，页面显示链头哈希。

### 场景 B：合规取证（追溯 + 报告）

1. 合规人员按 `actor=alice & action=perm_change` 追溯 → 得到 3 条记录；
2. 对其中一条点击"上下文" → 看到前后各 5 条操作（登录 → 改权限 → 导出）；
3. 导出审计报告 → 报告附带区间验证结果，可直接作为取证材料。

### 场景 C：篡改检测演练（验证 + 归档联动）

1. 写入 1500 条记录，触发自动归档（阈值 1000）→ 生成批次 #1；
2. 手工 UPDATE 主库某条记录的 `target`（模拟入侵）；
3. 前端执行"完整验证" → 报告 `status=hash_mismatch, break_seq=952`；
4. 定位到 952 号条目，比对哈希确认被改。

### 场景 D：迁移升级

1. 旧版本库只有 v1 schema；升级二进制后启动 → 自动执行 v2、v3 迁移；
2. 迁移日志显示版本 1 → 3；`schema_migrations` 表记录完整；
3. 迁移后全链验证通过，确认迁移未破坏链。

## 13. 非功能需求

| 类别 | 要求 |
| --- | --- |
| 性能 | 单机顺序写入 ≥ 1000 条/秒（SQLite WAL）；全链验证 10 万条 < 5s |
| 可用性 | 单进程 + 单文件部署；崩溃恢复依赖 SQLite 事务 |
| 安全 | SHA-256 哈希链 + 可选静态令牌；禁止 UPDATE/DELETE 审计表 |
| 可运维 | 健康检查、归档状态、统计接口；结构化日志（标准库 log/slog） |
| 可测试性 | 存储层接口化，可注入内存实现；验证算法纯函数化 |
| 代码约束 | Go 非测试代码 2000–2200 行、20–25 个文件（详见 docs/02） |
